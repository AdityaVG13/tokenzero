#1 critical Windows installer silently wipes HKCU\Environment\Path when value name is not exactly 'Path'
Impact
Data loss: existing user PATH entries are replaced by a single-entry value; rollback then *deletes* the value entirely instead of restoring it.
Contradicts: install docs 'records rollback data'
Evidence
windows_path.rs:69-88 (case-sensitive strip_prefix('Path')); install/lib.rs:518-583 (apply blindly uses None); install/lib.rs:628-637 (rollback enters delete branch because existed:false was persisted in the manifest).
Repro
On a machine where HKCU\Environment\Path was previously written by `setx PATH ...` from CMD (stored as PATH or path), run `tokenzero install --apply` then `tokenzero install --rollback latest`. User PATH is empty.
Fix sketch
Match the value name case-insensitively; treat parse-miss with exit-0 as fatal abort; in rollback() re-check live registry state before deleting when entry.existed is false.

code review #1 + #5
#2 critical tz:// refs use only 64 bits of SHA-256 and overwrite on collision
Impact
`expand` can silently return wrong bytes for a valid ref, breaking the core 'byte-exact recoverable' invariant.
Contradicts: docs/racc.md:45 'dangling refs never return wrong bytes'
Evidence
core/lib.rs:1528-1536 truncates SHA-256 to 8 bytes; recovery/lib.rs:559-562 inserts by id with no length/hash verification.
Fix sketch
Store full SHA-256 hash + length alongside the ref id; verify on expand; collision bucket or refuse to serve on detected collision.
Source
design review #5
#3 critical Refs can be evicted before the response that advertises them returns
Impact
A single large payload or cache-pressure event can hand the agent a `tz://` it cannot expand. Capsule-level liveness check happens before the persist, eviction happens after.
Contradicts: README 'byte-exact recoverable'; docs/racc.md:55 'exact refs with no dangling handles'
Evidence
mcp/lib.rs:355-356, :446-490 (refs pushed before persist_pending, no re-check); recovery/lib.rs:681-779 (evict runs before write, drops oldest live refs while over max_bytes).
Fix sketch
Pin the current response's refs through persist, or re-verify with has_ref after eviction; if they can't fit, return degraded output with no refs or atomically expand capacity for the current call.
Source
design review #2
#4 high MCP traffic is not Pulse-accounted; 'savings after recovery' is untrue on the main integration surface
Impact
`tz_expand` calls over MCP never charge recovery tokens back to the original serve, so the headline RACC accounting claim does not hold for agent-routed usage (the only real-world surface).
Contradicts: README 'Savings are counted after any recovery'
Evidence
mcp/tools.rs:14-21 (MCP dispatch returns response with no Pulse write); CLI commands DO call record_tool_pulse at tokenzero/src/main.rs:448, :719; pulse events lack session/call ids (pulse/src/lib.rs:19-35; docs/pulse.md:220-223).
Fix sketch
Instrument Pulse at the MCP tools/call boundary (including tz_expand); include stable session/call/ref ids so recovery can be attributed back to the original serve.

design review #1
#5 high `tz_fetch` is an unrestricted SSRF / exfiltration primitive
Impact
Any MCP-capable agent can fetch arbitrary http(s) URLs (loopback, link-local, cloud metadata endpoints, internal services) and cache the bodies behind refs.
Evidence
mcp/tools.rs:201-209 (fetch exposed unconditionally); mcp/lib.rs:1674-1718 (only checks http(s) prefix, then invokes `curl -sS -L`).
Fix sketch
Default to network-off; add allow/deny lists; block loopback, RFC1918, link-local, and metadata IPs after DNS resolution; cap redirects; log fetches as security-relevant telemetry.

design review #4
#6 high Supervisor can send both a retryable error and a real response for the same JSON-RPC id
Impact
Strict MCP clients may treat duplicate replies as protocol violations and tear down the session; resent reply also hardcodes framed=false.
Contradicts: README 'crash-transparent supervisor'
Evidence
mcp/supervisor.rs:157-166 (tracks request, stores as pending_resend on failed write), :424-438 (drains all outstanding ids with retryable errors), :451-453 + :475-484 (resend with framed=false).
Fix sketch
For a message known not to reach the child, remove its id from outstanding before emitting retryable errors; preserve original framing on resend; return either an error or a replay, never both.

design review #3
#7 high `collect_search` / `collect_glob` recurse forever on symlink loops inside an allowed root
Impact
Single `tz_find` or `tz_glob` against a tree with a symlink cycle → stack overflow / wall-clock DoS. `collect_tree` is depth-bounded; these two aren't, which makes the asymmetry hard to spot in review.
Evidence
mcp/collect.rs:177-251 (collect_search), :493-534 (collect_glob); both call path.is_dir() which follows links; no visited-set, no depth bound. max_files only stops when results vector is full.
Fix sketch
Mirror collect_tree's depth bound; skip entries where file_type.is_symlink(); or switch to walkdir::WalkDir::new().follow_links(false).max_depth(N).

code review #3
#8 high `record_fetch` corrupts/loses the fetch index under any concurrency or crash
Impact
Two concurrent tz_fetch calls (4-worker MCP pool or two processes against the same cache) silently lose entries; a crash mid-write leaves truncated JSON and load_fetch_index then returns default(), mass-invalidating all previously cached fetches.
Evidence
mcp/lib.rs:2285-2315 uses std::fs::write (truncate+write) with no lock, no atomic temp+rename, no sync_data; load_fetch_index at :2271-2276 swallows parse errors.
Fix sketch
Reuse the recovery crate's atomic_write_json pattern (sibling-tmp + fs4 lock + sync_data + rename + counter-nonce tmp name).

code review #2
#9 high MCP session dedup race — README's headline 99.7% repeat-read benchmark does not reproduce
Impact
The 'session dedup' feature exists (SessionMemory + unchanged_read_note, on by default) but is not enforced across pipelined requests in the 4-worker pool. README benchmark row '16,712 → 45 (99.7%)' is unreproducible.
Contradicts: README benchmark row 'Re-read the same file (session dedup): 16,712 → 45 tokens, 99.7%'
Evidence
EMPIRICAL: two pipelined `tools/call read` requests on the same MCP session return byte-identical 732-char responses (185 vs 150 visible tokens — observed in this demo). Feature: session.rs:22-92, lib.rs:380-405. Worker pool: stdio.rs:37-44, :93-103. First read does not update session memory until persist completes (lib.rs:446-519). Benchmark harness uses `sleep 1` instead of response-gated send: scripts/benchmark_tokens.sh:52-63.
Fix sketch
Serialize same-key reads via an in-flight-serve table keyed by ServeKey; second identical request waits for the first to persist, then emits unchanged note. Fix the benchmark to await response id=2 before sending id=3. Re-run README numbers from the fixed harness.

Impact
What's cached is the rewritten command's bytes, not the user's original command. Test failures hidden by -q can't be recovered.
Evidence

Fix sketch
Do not rewrite output semantics by default; if quiet rewriting stays, mark explicitly lossy and exclude from exact-output claims.

Impact

Evidence

design review #7
#12 medium `tz_edit` write race + missing fsync; doc claim overstates crash safety
Impact
Two same-PID workers editing the same path interleave bytes in the shared tmp file; no fsync/parent-sync means power loss between rename and data-flush can leave the user's file truncated.
Evidence
mcp/render.rs:253-271 — tmp is `.{file}.tz-edit-{pid}` (no per-call nonce), no create_new, no advisory lock; fs::write with no sync_data. Compare recovery/lib.rs:1069+:1248-1259 which uses AtomicUsize+create_new+sync_data.
Fix sketch
Add process-wide AtomicUsize counter for tmp suffix; create_new(true); sync_data before rename; best-effort parent-dir sync_all.
